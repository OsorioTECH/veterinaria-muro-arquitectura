1. Visión y selección tecnológica

Volver a Entrega 1 Inicio

Se construirá una aplicación web para la clínica veterinaria: registrar clientes, mascotas, citas, servicios, exámenes y facturas. La idea es que sea muy rápida, segura, fácil de mantener y que podamos desarrollarla sin enredarnos con demasiada programación innecesaria.

Stack elegido

  • Backend Java 17 + Spring Boot 3.x
    Qué es: “Spring Boot” ahorra código repetido al crear APIs en Java.

    Traducción: avanzamos más rápido con menos dolor.

  • Base de datos (Producción) PostgreSQL 15
    Qué es: base de datos robusta y gratuita.

    Traducción: datos ordenados y confiables.

  • Base de datos (Desarrollo) H2 en memoria
    Qué es: base “rápida de prueba” en memoria. Traducción: ideal para desarrollar sin instalar nada complejo.
  • Documentación API Swagger/OpenAPI (springdoc)
    Qué es: página interactiva para probar la API. Traducción: probamos endpoints en el navegador.
  • Seguridad Spring Security con JWT y roles
    Qué es: protege la API con inicios de sesión y permisos. Traducción: solo quien debe, puede ver o cambiar info.
  • Control de versiones Git + GitHub
    Qué es: historial y respaldo del trabajo con ramas por entrega.

Objetivos

  • Velocidad de desarrollo con buenas prácticas.
  • Arquitectura limpia y modular.
  • Seguridad y mantenibilidad desde el inicio.

7. Estructura del proyecto (carpetas ordenadas)

Volver a Entrega 1 Inicio

Esta estructura imita cómo organizan proyectos los equipos profesionales: separamos por módulos (dominio, aplicación, infraestructura, API).

vete/ ├─ pom.xml ├─ README.md ├─ .gitignore ├─ docker-compose.yml ├─ .env.example ├─ vete-domain/ │ ├─ pom.xml │ └─ src/main/java/com/vete/domain/... ├─ vete-application/ │ ├─ pom.xml │ └─ src/main/java/com/vete/application/... ├─ vete-infrastructure/ │ ├─ pom.xml │ └─ src/main/java/com/vete/infrastructure/... └─ vete-api/ ├─ pom.xml └─ src/main/java/com/vete/api/...

Cómo se conecta todo (flujo típico)

  1. El Controller recibe una petición HTTP con un DTO.
  2. Valida el DTO y llama a un Use Case en application.
  3. El Use Case usa el Dominio (entidades/servicios) para aplicar reglas.
  4. Cuando necesita datos, llama a un Repositorio del Dominio (interface).
  5. Un Adapter en infrastructure implementa ese repositorio usando Spring Data JPA y mapea a entidades JPA.
  6. Se persiste en la BD, se regresa el resultado al Use Case, luego al Controller y se responde con un DTO.
DTO: objeto simple para enviar/recibir datos por la API (sin lógica). JPA: estándar para mapear objetos a tablas. Adapter: traductor entre dominio y tecnología.

Ejemplo mínimo de archivos clave

package com.vete.domain.repository; import java.util.Optional; import com.vete.domain.model.Cliente; public interface ClienteRepository { Optional<Cliente> findByCedula(String cedula); Cliente save(Cliente cliente); } package com.vete.infrastructure.persistence.repository; import java.util.Optional; import org.springframework.data.jpa.repository.JpaRepository; import com.vete.infrastructure.persistence.entity.ClienteEntity; public interface ClienteJpaRepository extends JpaRepository<ClienteEntity, Long> { Optional<ClienteEntity> findByCedula(String cedula); } package com.vete.infrastructure.persistence.adapter; import java.util.Optional; import org.springframework.stereotype.Component; import lombok.RequiredArgsConstructor; import com.vete.domain.repository.ClienteRepository; import com.vete.domain.model.Cliente; import com.vete.infrastructure.persistence.repository.ClienteJpaRepository; import com.vete.infrastructure.persistence.entity.ClienteEntity; import com.vete.infrastructure.mapper.ClienteEntityMapper; @Component @RequiredArgsConstructor public class ClienteRepositoryAdapter implements ClienteRepository { private final ClienteJpaRepository jpa; private final ClienteEntityMapper mapper; @Override public Optional<Cliente> findByCedula(String cedula) { return jpa.findByCedula(cedula).map(mapper::toDomain); } @Override public Cliente save(Cliente cliente) { ClienteEntity saved = jpa.save(mapper.toEntity(cliente)); return mapper.toDomain(saved); } }

El dominio no depende de JPA ni de Spring; Infraestructura traduce entre dominio y BD.

ADR-001 · Estrategia de Autenticación de Usuarios

Volver a ADRs Inicio

Contexto: Necesitamos autenticación segura por rol (ADMIN, VET, AUX, CLIENTE) para web y móvil, con escalabilidad horizontal.

Decisión: Autenticación stateless con JSON Web Tokens (JWT) firmados (HS256 inicialmente), enviados en el encabezado Authorization: Bearer. Refresco mediante tokens de refresh con rotación y expiración corta para el access token.
Consecuencias: + Escalable (sin sesión en servidor), compatible con múltiples clientes, fácil integración con gateways. − Requiere manejo de revocación (lista negra o invalidación por versión de token), no poner datos sensibles en el payload.
// Pseudocódigo de validación (Aplicación/Infra) if (!authHeader.startsWith("Bearer ")) deny(); String jwt = authHeader.substring(7); Claims c = jwtService.verify(jwt); // firma + expiración authorize(c.role()); // mapea a permisos

ADR-002 · Manejo de Errores y Generación de Logs

Volver a ADRs Inicio

Contexto: Errores son inevitables. Necesitamos feedback claro al usuario y trazabilidad para desarrollo.

Decisión: Doble canal: mensajes de error amigables y consistentes en UI (códigos y textos mapeados) y logging estructurado en servidor (JSON) con niveles (INFO/WARN/ERROR), correlación por request-id y captura centralizada de excepciones.
Consecuencias: + Mejor UX, diagnósticos rápidos, observabilidad. − Requiere estandarizar códigos y disciplina en los niveles de log.
// Ejemplo de cuerpo de error (API) { "code": "CLIENTE_NO_ENCONTRADO", "message": "No pudimos encontrar ese cliente.", "traceId": "f1a2..." }

ADR-003 · Consumo de APIs Externas

Volver a ADRs Inicio

Contexto: Integraciones con pago, notificaciones, IA, etc., pueden cambiar.

Decisión: Capa de Adaptadores/Servicios externos en Infraestructura con interfaces (puertos) en Dominio/Aplicación. Timeouts, reintentos con backoff, circuit breaker y mapeo de errores a nuestras excepciones.
Consecuencias: + Bajo acoplamiento, reemplazo de proveedor sin tocar negocio. − Más componentes y pruebas de contrato.
// Puerto (Aplicación) interface PagoGateway { PagoResult cobrar(PagoRequest r); } // Adaptador (Infra) class PagoStripeAdapter implements PagoGateway { /* ... */ }

ADR-004 · Integración de Inteligencia Artificial (IA)

Volver a ADRs Inicio

Contexto: Se planea asistente para agendar citas y responder consultas básicas.

Decisión: Usar proveedor externo (OpenAI/Vertex AI) vía API a través de un adaptador de IA. Datos sensibles anonimizados antes de enviar. Limitar prompts y costos con cuotas y caching.
Consecuencias: + Time-to-market rápido, calidad de modelo. − Dependencia del proveedor y costos variables; se mitiga con abstracción y estrategia de fallback.
// Puerto IA interface AsistenteIA { Respuesta asistir(Peticion p); }

ADR-005 · Flexibilidad para Cambios de Tecnología

Volver a ADRs Inicio

Contexto: Tecnologías cambian (frameworks, runtimes, UI).

Decisión: Arquitectura en capas (Presentación, Aplicación, Dominio, Infraestructura) con dependencias hacia dentro. Contratos en Dominio/Aplicación y detalles en Infraestructura. Uso de patrones Strategy, Factory, Observer para extensibilidad.
Consecuencias: + Reemplazo de UI o persistencia con impacto mínimo. − Curva inicial de diseño y disciplina en límites.

ADR-006 · Estrategia para Migraciones de Base de Datos

Volver a ADRs Inicio

Contexto: Posibles cambios de motor (MySQL ↔ PostgreSQL) y evolución de esquema.

Decisión: ORM (Hibernate/JPA) + migraciones con Flyway. Repositorios como puertos. SQL nativo solo cuando sea necesario y encapsulado.
Consecuencias: + Portabilidad y control de versiones del esquema. − Requiere disciplina en migraciones y pruebas de performance.
// Ejemplo Flyway V1__crear_tablas_basicas.sql V2__agregar_indice_citas.sql

ADR-007 · Soporte para Múltiples Idiomas (i18n)

Volver a ADRs Inicio

Contexto: Usuarios de distintos idiomas (zona turística).

Decisión: Internacionalización con archivos de recursos por idioma (ej. textos_es.json, textos_en.json) y detección de locale. No hardcodear textos en la UI.
Consecuencias: + Añadir idiomas sin tocar código. − Requiere proceso de traducción y validación de contexto.
// Estructura i18n/ ├─ es.json └─ en.json

ADR-008 · Funcionalidad de Búsqueda

Volver a ADRs Inicio

Contexto: Búsqueda de clientes, mascotas e historiales.

Decisión: Búsqueda inicial con consultas SQL sobre campos indexados, paginación y filtros. Diseñar puerto para integrar Elasticsearch a futuro sin romper contratos.
Consecuencias: + Simple y económica al inicio. − Requiere estrategia de escalado (caché, índices compuestos) antes de migrar a motor dedicado.
// Índices recomendados CREATE INDEX idx_cliente_nombre ON cliente(nombre); CREATE INDEX idx_mascota_duenio ON mascota(duenio_id);

ADR-009 · Generación de Informes y Reportes

Volver a ADRs Inicio

Contexto: Facturas, historias clínicas, recetas en PDF.

Decisión: Módulo de reportes con librería especializada (JasperReports) y plantillas (.jrxml) versionadas. Generación asíncrona para reportes pesados.
Consecuencias: + Cambios de diseño sin tocar código; mejor rendimiento. − Curva de aprendizaje de plantillas.

ADR-010 · Conexión con Redes Sociales (OAuth 2.0)

Volver a ADRs Inicio

Contexto: Registro/Inicio rápido con Google/Facebook.

Decisión: OAuth 2.0 y OpenID Connect con SDKs oficiales, validación del id_token y vinculación de cuentas a nuestro usuario interno.
Consecuencias: + Mejor UX, menos gestión de contraseñas. − Manejo de flujos y cambios de políticas de los proveedores.

ADR-011 · Cumplimiento de Protección de Datos (GDPR)

Volver a ADRs Inicio

Contexto: Datos personales y clínicos sensibles.

Decisión: Cifrado en tránsito (TLS) y en reposo (campos sensibles), control de acceso por roles, consentimiento explícito, registro de auditoría, y mecanismos para ejercer derechos (acceso, rectificación, borrado).
Consecuencias: + Cumplimiento legal y confianza del usuario. − Esfuerzo adicional en procesos y documentación.

ADR-012 · Inclusión y Accesibilidad (WCAG)

Volver a ADRs Inicio

Contexto: Uso por personas con diversas capacidades.

Decisión: Seguir WCAG 2.1 AA: contraste, tamaños legibles, navegación por teclado, etiquetas/ARIA, focus visible, textos alternativos y validación de formularios accesible.
Consecuencias: + Acceso universal y cumplimiento normativo. − Requiere revisiones UX y pruebas con lectores de pantalla.

ADR-013 · Diseño Adaptable (Responsivo)

Volver a ADRs Inicio

Contexto: Acceso desde desktop, tablet y móvil.

Decisión: CSS Grid/Flex, breakpoints y componentes fluidos; evitar valores fijos donde no aporten; imágenes responsivas.
Consecuencias: + UX consistente en cualquier dispositivo. − Trabajo adicional en pruebas multi-dispositivo.

ADR-014 · Manejo de Versiones del Código (Git/GitFlow)

Volver a ADRs Inicio

Contexto: Colaboración, historial y releases estables.

Decisión: Git en GitHub con GitFlow (main, develop, feature/*, release/*, hotfix/*), PRs con revisión, CI para pruebas automáticas y versionado semántico.
Consecuencias: + Flujo ordenado, menos regresiones, trazabilidad. − Requiere disciplina en ramas y revisiones.

9. Calidad, rendimiento y seguridad

Volver a Entrega 1 Inicio

Rendimiento

  • Paginación en listados grandes.
  • Índices en cédula y fecha de cita.
  • Caché para catálogos estables.

Seguridad

  • JWT + roles: ADMIN, VET, AUX, CLIENTE.
    JWT: pase digital firmado que el cliente envía en cada petición; el servidor verifica la firma para identidad y permisos.
  • Contraseñas con BCrypt.
    BCrypt: hash irreversible con sal y costo; protege incluso si filtran la base.
  • Auditoría básica (quién/cuándo).
    Campos creadoPor/creadoEn/actualizadoPor/actualizadoEn para trazabilidad.

Mantenimiento

  • Pruebas con H2.
    BD en memoria para pruebas rápidas.
  • Nombres claros y consistentes.
  • ADRs documentadas.
    Registro corto de decisiones y consecuencias.

Strategy · Cálculo de precio final

Volver a Entrega 2 Inicio

Cada regla de precio es una estrategia independiente (descuento frecuente, promo por especie, impuesto por servicio). Se encadenan con un compositor. Cambias reglas sin tocar el caso de uso.

package com.vete.domain.pricing; // Contrato: todas las reglas implementan este método. public interface PricingStrategy { Money calculate(Money base, PricingContext ctx); } package com.vete.domain.pricing; import java.math.BigDecimal; // VO Money: seguro e inmutable para manejar dinero. public record Money(BigDecimal amount, String currency) { public Money add(Money other) { if (!this.currency.equals(other.currency)) throw new IllegalArgumentException("Moneda distinta"); return new Money(this.amount.add(other.amount), this.currency); } public Money multiply(double factor) { return new Money(this.amount.multiply(BigDecimal.valueOf(factor)), this.currency); } } package com.vete.domain.pricing; // Contexto mínimo para decidir si aplica cada regla. public record PricingContext(String clienteCategoria, String especie, String servicioCodigo) {} package com.vete.domain.pricing.impl; import com.vete.domain.pricing.*; // FRECUENTE => -10% public class FrequentClientDiscount implements PricingStrategy { @Override public Money calculate(Money base, PricingContext ctx) { return "FRECUENTE".equalsIgnoreCase(ctx.clienteCategoria()) ? base.multiply(0.90) : base; } } package com.vete.domain.pricing.impl; import com.vete.domain.pricing.*; // GATO => -5% public class SpeciesPromoStrategy implements PricingStrategy { @Override public Money calculate(Money base, PricingContext ctx) { return "GATO".equalsIgnoreCase(ctx.especie()) ? base.multiply(0.95) : base; } } package com.vete.domain.pricing.impl; import com.vete.domain.pricing.*; // CIRUGIA => +5% impuesto public class ServiceTaxStrategy implements PricingStrategy { @Override public Money calculate(Money base, PricingContext ctx) { return "CIRUGIA".equalsIgnoreCase(ctx.servicioCodigo()) ? base.multiply(1.05) : base; } } package com.vete.domain.pricing; import java.util.List; // Compositor: aplica N estrategias en orden. public class CompositePricing implements PricingStrategy { private final List<PricingStrategy> strategies; public CompositePricing(List<PricingStrategy> strategies) { this.strategies = strategies; } @Override public Money calculate(Money base, PricingContext ctx) { Money result = base; for (PricingStrategy s : strategies) result = s.calculate(result, ctx); return result; } } package com.vete.application.pricing; import com.vete.domain.pricing.*; import com.vete.domain.pricing.impl.*; import java.math.BigDecimal; import java.util.List; // Aplicación: decide qué reglas están activas hoy. public class PricingService { public Money calcularPrecio(String servicioCodigo, String especie, String clienteCategoria, BigDecimal base) { PricingContext ctx = new PricingContext(clienteCategoria, especie, servicioCodigo); PricingStrategy strategy = new CompositePricing(List.of( new FrequentClientDiscount(), new SpeciesPromoStrategy(), new ServiceTaxStrategy() )); return strategy.calculate(new Money(base, "COP"), ctx); } }
Nota explicativa: dividimos el cálculo en reglas pequeñas y encadenables (descuentos, promos, impuestos). Escenario real: precio base 100.000 COP → cliente FRECUENTE (-10%) = 90.000 → especie GATO (-5%) = 85.500 → servicio CIRUGIA (+5%) = 89.775 COP. Flexibilidad: añadir/quitar/reordenar reglas sin tocar el caso de uso ni otras clases; nuevas campañas se integran creando otra estrategia.

Factory · Creación de usuarios por rol

Volver a Entrega 2 Inicio

Centraliza la construcción de usuarios (ADMIN, VET, AUX, CLIENTE). Consistencia sin duplicar lógica en controladores o casos de uso.

package com.vete.domain.user; // Entidad simple (Dominio) public class Usuario { private final String username; private final String role; // ADMIN, VET, AUX, CLIENTE private final boolean active; public Usuario(String username, String role, boolean active) { this.username = username; this.role = role; this.active = active; } public String getUsername() { return username; } public String getRole() { return role; } public boolean isActive() { return active; } } package com.vete.domain.user; // Parámetros de creación (Dominio) public record UsuarioParams(String username, String role) {} package com.vete.application.user; // Factory (Aplicación): estandariza defaults por rol. import com.vete.domain.user.Usuario; import com.vete.domain.user.UsuarioParams; public class UsuarioFactory { public Usuario create(UsuarioParams params) { return switch (params.role()) { case "ADMIN" -> new Usuario(params.username(), "ADMIN", true); case "VET" -> new Usuario(params.username(), "VET", true); case "AUX" -> new Usuario(params.username(), "AUX", true); case "CLIENTE" -> new Usuario(params.username(), "CLIENTE", true); default -> throw new IllegalArgumentException("Rol no soportado: " + params.role()); }; } } package com.vete.application.user; // Uso típico (Aplicación): registro consistente. import com.vete.domain.user.Usuario; import com.vete.domain.user.UsuarioParams; public class RegistroUsuarioService { private final UsuarioFactory factory; public RegistroUsuarioService(UsuarioFactory factory) { this.factory = factory; } public Usuario registrar(String username, String role) { Usuario nuevo = factory.create(new UsuarioParams(username, role)); // Persistir vía repositorio del dominio (puerto)... return nuevo; } }
Nota explicativa: centralizamos la creación de usuarios por rol para garantizar valores correctos y consistentes. Escenario real: registrar("ana","VET") → Usuario{username="ana", role="VET", active=true}; si llega un rol no soportado, la fábrica lo rechaza de forma uniforme. Flexibilidad: agregar un nuevo rol (p. ej., "ADMIN_AUDITOR") solo requiere extender la Factory, sin tocar controladores ni casos de uso.

Observer · Notificaciones por eventos

Volver a Entrega 2 Inicio

Desacopla efectos secundarios (email/SMS) del caso de uso. Los suscriptores reaccionan a eventos del dominio sin tocar la lógica principal.

private final String clienteEmail; private final long occurredAt = System.currentTimeMillis(); public CitaCreadaEvent(String citaId, String clienteEmail) { this.citaId = citaId; this.clienteEmail = clienteEmail; } public String citaId() { return citaId; } public String clienteEmail() { return clienteEmail; } public String type() { return "CITA_CREADA"; } public long occurredAt() { return occurredAt; } } package com.vete.domain.events; // Contrato de suscriptor (Dominio) public interface DomainEventSubscriber<E extends DomainEvent> { boolean supports(String type); void onEvent(E event); } package com.vete.application.events; import com.vete.domain.events.*; import java.util.ArrayList; import java.util.List; // Bus simple (Aplicación): publica a suscriptores compatibles. public class SimpleEventBus { private final List<DomainEventSubscriber<? super DomainEvent>> subs = new ArrayList<>(); public void subscribe(DomainEventSubscriber<? super DomainEvent> s) { subs.add(s); } public void publish(DomainEvent event) { for (var s : subs) if (s.supports(event.type())) s.onEvent(event); } } package com.vete.infrastructure.notifications; import com.vete.domain.events.*; // Email (Infraestructura) public class EmailNotificacionSubscriber implements DomainEventSubscriber<DomainEvent> { public boolean supports(String type) { return "CITA_CREADA".equals(type); } public void onEvent(DomainEvent event) { if (event instanceof CitaCreadaEvent e) System.out.println("EMAIL → Cita " + e.citaId() + " a " + e.clienteEmail()); } } package com.vete.infrastructure.notifications; } public void onEvent(DomainEvent event) { if (event instanceof CitaCreadaEvent e) System.out.println("SMS → Cita " + e.citaId() + " para " + e.clienteEmail()); } } package com.vete.application.citas; public CrearCitaUseCase(SimpleEventBus eventBus) { this.eventBus = eventBus; } public String crearCita(String clienteEmail, String mascotaId, String servicioCodigo) { String citaId = java.util.UUID.randomUUID().toString(); // ...validar y persistir vía repositorios (puerto)... eventBus.publish(new CitaCreadaEvent(citaId, clienteEmail)); return citaId; } } package com.vete.infrastructure.config; import com.vete.application.events.SimpleEventBus; import com.vete.infrastructure.notifications.*; // Bootstrap: suscribe canales. public class EventConfig { public static SimpleEventBus eventBus() { SimpleEventBus bus = new SimpleEventBus(); bus.subscribe(new EmailNotificacionSubscriber()); bus.subscribe(new SmsNotificacionSubscriber()); return bus; } }
Nota explicativa: el caso de uso publica eventos y los canales (email/SMS) reaccionan como suscriptores independientes. Escenario real: al crear una cita se emite CITA_CREADA → EmailSubscriber envía correo y SmsSubscriber envía SMS. Flexibilidad: sumar canales (Push, Webhook) se hace agregando nuevos suscriptores, sin modificar la lógica de crear cita ni rehacer pruebas del caso de uso.
