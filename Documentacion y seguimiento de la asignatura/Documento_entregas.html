1. Visión y selección tecnológica

Se construirá una aplicación web para la clínica veterinaria: registrar clientes, mascotas, citas, servicios, exámenes y facturas. La idea es que sea muy rápida, segura, fácil de mantener y que podamos desarrollarla sin enredarnos con demasiada programación innecesaria.

Stack elegido

  • Backend Java 17 + Spring Boot 3.x
    Qué es: “Spring Boot” es un marco que nos ahorra mucho código repetido al crear APIs en Java. Traducción: nos deja avanzar más rápido con menos dolor.
  • Base de datos (Producción) PostgreSQL 15
    Qué es: una base de datos robusta y gratuita. Traducción: guarda datos ordenados y confiables.
  • Base de datos (Desarrollo) H2 en memoria
    Qué es: una base de datos “rápida de prueba” que vive en la memoria del computador. Traducción: ideal para desarrollar sin instalar nada complejo.
  • Documentación API Swagger/OpenAPI (springdoc)
    Qué es: genera una página interactiva para probar la API. Traducción: podemos ver y probar los endpoints en el navegador sin usar otras herramientas.
  • Seguridad Spring Security con JWT y roles
    Qué es: protege la API con inicios de sesión y permisos. Traducción: solo quien debe, puede ver o cambiar información.
  • Control de versiones Git + GitHub
    Qué es: historial y respaldo del código. Traducción: si nos equivocamos, podemos volver atrás.

¿Por qué este stack?

  • Avanzamos rápido: Spring Boot quita mucha configuración manual.
  • Calidad de entrada: validaciones, seguridad y pruebas bien soportadas.
  • Buen rendimiento: PostgreSQL es veloz y estable; H2 acelera el desarrollo local.
  • Fácil de mantener: todo organizado por capas y con decisiones registradas.
  • Listo para crecer: luego podemos dividir en módulos o microservicios si hace falta.

2. Arquitectura por capas (la organización de la casa)

Dividimos el sistema en “pisos” (capas). Cada capa tiene su rol. Esto nos ayuda a entender mejor el código, a probar partes por separado y a cambiar una cosa sin dañar todo.

[Cliente / Navegador] │ ▼ Capa de Presentación (Controladores REST y DTOs: reciben y devuelven datos) │ ▼ Capa de Aplicación (Casos de uso: la orquesta que coordina la lógica) │ ▼ Capa de Dominio (Reglas del negocio: entidades y validaciones de fondo) │ ▼ Capa de Infraestructura (Guardado en BD, repositorios, configuraciones)

Qué hace cada capa

  • Presentación: expone la API, valida lo que llega y lo que sale. No contiene reglas de negocio.
  • Aplicación: ejecuta casos de uso (por ejemplo, “agendar cita”), maneja transacciones.
  • Dominio: es el corazón: entidades como Cliente, Mascota, Cita y sus reglas.
  • Infraestructura: cómo guardamos, leemos y configuramos cosas (BD, seguridad, etc.).

Beneficios

  • Más fácil de entender y cambiar.
  • Podemos probar cada parte sin depender de todo lo demás.
  • Si un día cambiamos de base de datos o de framework, el impacto es menor.
REST: una forma estándar de crear APIs en la web. DTO: “paquetes” de datos que enviamos o recibimos por la API.

3. Entidades de dominio (qué cosas existen en nuestro negocio)

Estas son las “piezas” principales que maneja la veterinaria. Estas seran las tablas en la BD y las clases en el código.

Modelo base

  • Cliente: id, cédula, nombre, apellidos, dirección, email, teléfono.
  • Mascota: id, nombre, fechaNacimiento, especie, raza, sexo, propietario (Cliente).
  • Veterinario: id, cédula, nombre, apellidos, teléfono, email.
  • Cita: id, fechaHora, estado, motivo, cliente, mascota, veterinario.
  • Servicio: id, nombre, duración (min), precioBase.
  • ExamenClinico: id, mascota, veterinario, fechaHora, resultados, observaciones.
  • Factura: id, fechaHoraPago, total, medioPago, cliente, atendidoPor (veterinario).
  • Usuario: id, nombre, apellido, email, contraseñaEncriptada, rol.

Reglas sencillas

  • Cada Mascota tiene un dueño (Cliente).
  • Una Cita une a Cliente, Mascota y Veterinario. Evitamos traslapar citas del mismo veterinario.
  • Una Factura puede tener varios ítems (servicios) y el total se calcula.
  • Usuario maneja el inicio de sesión y permisos (ADMIN, VET, AUX, CLIENTE).
Diagrama lógico rápido
Cliente (id, cedula, nombre, apellidos, direccion, email, telefono) 1 ─── * Mascota (id, nombre, fechaNacimiento, especie, raza, sexo, cliente_id) Veterinario (id, cedula, nombre, apellidos, telefono, email) Cita (id, fechaHora, estado, motivo, cliente_id, mascota_id, veterinario_id) Regla: no traslapar por (veterinario_id, rangoFechaHora) Servicio (id, nombre, duracionMin, precioBase) ExamenClinico (id, mascota_id, veterinario_id, fechaHora, resultadosJSON, observaciones) Factura (id, fechaHoraPago, total, medioPago, cliente_id, atendidoPor_vet_id) FacturaItem (id, factura_id, servicio_id, cantidad, precioUnit, subtotal)
Resultados JSON: guardamos algunos resultados de examen en formato flexible tipo “diccionario” (clave-valor), útil cuando cambian los campos.

4. Persistencia y base de datos (dónde y cómo guardamos)

Guardar los datos bien es clave: deben ser seguros, consistentes y rápidos de consultar. Usaremos dos bases: una para trabajar rápido en tu máquina mientras desarrollas (H2, liviana y en memoria) y otra “seria” para producción (PostgreSQL, estable y potente). Para cambiar entre una y otra, activamos “perfiles” (modos) en la configuración.

Perfiles de ejecución y configuración (application.yml)

Este archivo le dice a la app cómo conectarse a la base de datos según el modo: dev (desarrollo) o prod (producción).

spring: datasource: url: jdbc:h2:mem:vete;DB_CLOSE_DELAY=-1;MODE=PostgreSQL username: sa password: jpa: hibernate: ddl-auto: update show-sql: true properties: hibernate.format_sql: true profiles: active: dev --- spring: config: activate: on-profile: prod datasource: url: jdbc:postgresql://db:5432/vete username: vete_app password: ${DB_PASSWORD} jpa: hibernate: ddl-auto: validate properties: hibernate.jdbc.lob.non_contextual_creation: true management: endpoints.web.exposure.include: health,info
Perfil: “modo” de ejecución. dev (desarrollo) usa H2 para ir rápido; prod (producción) usa PostgreSQL para estabilidad.
H2 en memoria: no requiere instalación, arranca en segundos; ideal para pruebas locales.
MODE=PostgreSQL: hace que H2 se comporte parecido a PostgreSQL, evitando sorpresas al pasar a producción.
ddl-auto: controla cómo se crean/actualizan tablas. En dev “update” agiliza cambios; en prod “validate” evita cambios automáticos peligrosos.
${DB_PASSWORD}: variable de entorno. Nunca pongas contraseñas reales dentro del repositorio.
¿Cómo activo un perfil?
Maven/Java: agregar -Dspring.profiles.active=dev o prod al ejecutar.
IDE: en “Run/Debug Configurations”, agrega el perfil activo.

Esquema de tablas e índices resumidamente propuesto

Un buen diseño en BD acelera consultas y evita datos incoherentes. Por lo que esta seccion es de vital importancia para el proyecto. Este es un esquema de las tablas y sus relaciones.

Cliente(id PK, cedula UNIQUE, nombre, apellidos, direccion, email UNIQUE, telefono) Mascota(id PK, nombre, fecha_nacimiento, especie, raza, sexo, cliente_id FK -> Cliente.id) Veterinario(id PK, cedula UNIQUE, nombre, apellidos, telefono, email UNIQUE) Servicio(id PK, nombre UNIQUE, duracion_min, precio_base) Cita(id PK, fecha_hora, estado, motivo, cliente_id FK, mascota_id FK, veterinario_id FK) ExamenClinico(id PK, mascota_id FK, veterinario_id FK, fecha_hora, resultados_json, observaciones) Factura(id PK, fecha_hora_pago, total, medio_pago, cliente_id FK, atendido_por_vet_id FK) FacturaItem(id PK, factura_id FK, servicio_id FK, cantidad, precio_unit, subtotal) Índices sugeridos: - Cliente(cedula), Cliente(email) - Veterinario(cedula), Veterinario(email) - Cita(fecha_hora), Cita(veterinario_id, fecha_hora) - Mascota(cliente_id), Mascota(nombre)
PK (Primary Key): identifica de forma única una fila.
FK (Foreign Key): relaciona tablas y mantiene coherencia.
Índice: acelera búsquedas en columnas usadas con frecuencia.

Buenas prácticas de persistencia (estas son muy importantes tenerlas claras desde el inicio, ya que nos evitaran problemas en el futuro en cuestiones como la seguridad, la integracion con otras aplicaciones, la pérdida de datos por migraciones mal gestionadas, el bajo rendimiento en consultas por falta de índices y la dificultad de mantenimiento por esquemas inconsistentes, etc.)

  • Usa paginación en listados grandes (por ejemplo, citas del mes).
  • Define índices en campos que consultas seguido (cédula, fecha de cita).
  • Maneja transacciones en casos de uso que afectan varias tablas (crear factura + ítems).
  • No expongas entidades JPA directamente en la API: usa DTOs.
  • En producción, usa migraciones (Flyway o Liquibase) en vez de ddl-auto=update.
  • Configura pool de conexiones (HikariCP viene por defecto) con tamaños razonables.
Ejemplo básico de conexión con variables de entorno
SPRING_PROFILES_ACTIVE=prod DB_PASSWORD=una_password_segura SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:5432/vete SPRING_DATASOURCE_USERNAME=vete_app SPRING_JPA_HIBERNATE_DDL_AUTO=validate
Resumen práctico: en tu día a día desarrolla con H2 (rápido), valida el modelo; para producción usa PostgreSQL con migraciones y variables de entorno. Así ganas velocidad sin perder calidad ni seguridad.

Nota: estas son las buenas prácticas que se deben tener en cuenta para el proyecto segun el analisis realizado por nuestro equipo o grupo.

5. Repositorios (la capa que se comunica con la base de datos)

Un “repositorio” es como un asistente especializado en guardar y leer una entidad. Con Spring Data JPA, solo creamos una interfaz y este se encargara de la persistencia de los datos. Se planteo la creacion de repositorios para cada entidad, ya que es una buena practica y nos permite tener un codigo mas limpio y mantenible.

Ejemplos de repositorios

// Dominio (simplificado) @Entity class Cliente { @Id @GeneratedValue Long id; String cedula; String nombre; String apellidos; String email; } // Infraestructura - Repositorios public interface ClienteRepository extends JpaRepository<Cliente, Long> { Optional<Cliente> findByCedula(String cedula); boolean existsByEmail(String email); } public interface MascotaRepository extends JpaRepository<Mascota, Long> { List<Mascota> findByPropietarioId(Long clienteId); } public interface CitaRepository extends JpaRepository<Cita, Long> { @Query("select count(c)>0 from Cita c where c.veterinario.id=:vetId and c.fechaHora between :inicio and :fin and c.estado<> 'CANCELADA'") boolean existeSolape(@Param("vetId") Long vetId, @Param("inicio") LocalDateTime inicio, @Param("fin") LocalDateTime fin); }
JpaRepository: nos da gratis métodos como guardar, buscar por id, listar, borrar, etc.

Transacciones y reglas

@Service public class AgendaCitasService { private final CitaRepository citas; public AgendaCitasService(CitaRepository citas){ this.citas = citas; } @Transactional public Cita agendar(AgendarCitaCmd cmd){ if (citas.existeSolape(cmd.veterinarioId(), cmd.inicio(), cmd.fin())){ throw new NegocioException("Cita solapada"); } Cita c = Cita.crear(cmd); return citas.save(c); } }
@Transactional: asegura que el bloque completo se guarda como una unidad. Si algo falla, se revierte.

6. Capa de presentación (API REST con datos claros)

La API es la “puerta” por donde otras aplicaciones (o nuestro futuro frontend) hablan con el sistema. Enviamos y recibimos datos con formatos simples (JSON).

Controlador REST

@RestController @RequestMapping("/api/clientes") @RequiredArgsConstructor class ClienteController { private final ClienteAppService app; @PostMapping public ResponseEntity<ClienteDto> crear(@Valid @RequestBody CrearClienteDto dto){ return ResponseEntity.status(HttpStatus.CREATED).body(app.crear(dto)); } @GetMapping("/{id}") public ClienteDto byId(@PathVariable Long id){ return app.buscar(id); } }
Controller: recibe la petición, valida y pasa el trabajo a la capa de aplicación.

DTOs y validaciones

public record CrearClienteDto( @NotBlank String cedula, @NotBlank String nombre, @NotBlank String apellidos, @Email String email, String telefono, String direccion ) {} public record ClienteDto( Long id, String cedula, String nombre, String apellidos, String email ) {}
¿Qué es un DTO? DTO significa “Data Transfer Object” (Objeto de Transferencia de Datos). Es un objeto simple que usamos para enviar y recibir datos por la API. No tiene lógica de negocio, solo campos. ¿Para qué? Para no exponer directamente las entidades internas de la base de datos y así mantener el sistema más seguro y ordenado.
¿Por qué usamos records en Java para DTOs? Los records son una forma corta de declarar clases inmutables con campos, constructor y métodos básicos (equals, hashCode, toString) generados automáticamente. Traducción: menos código, más claridad, menos errores.
Validaciones: revisan que los datos que llegan tengan el formato correcto antes de procesarlos. - @NotBlank: el campo no puede venir vacío ni solo con espacios (ideal para nombre, cédula). - @Email: obliga a que el texto tenga forma de correo válido (por ejemplo nombre@dominio.com). - Puedes agregar otras como @Size(min=…), @Pattern(regex=…) o @NotNull según el caso.
¿Por qué dos DTOs distintos? CrearClienteDto es lo que el cliente envía al crear un registro (no incluye id porque aún no existe). ClienteDto es lo que devolvemos al usuario después de guardar o consultar (incluye el id asignado).
Buenas prácticas rápidas: no reutilices entidades JPA como DTOs, separa “lo que entra” de “lo que sale” con DTOs específicos, y valida siempre en el controlador o capa de presentación para proteger la lógica de negocio.
Swagger/OpenAPI: es la combinación de un estándar (OpenAPI) para describir tu API y una interfaz web (Swagger UI) que se genera automáticamente a partir de esa descripción. ¿Qué te da en la práctica? Una página interactiva donde puedes ver todos los endpoints de tu API, sus parámetros, ejemplos de entradas y salidas, códigos de error y probar las peticiones directamente desde el navegador sin usar herramientas externas. Esto ayuda a estudiantes y equipos a entender rápido “qué hace” cada ruta, reduce malentendidos entre frontend y backend (porque comparten el mismo “contrato” de la API) y acelera las pruebas durante el desarrollo. Normalmente se accede en /swagger-ui.html cuando tienes la dependencia de springdoc instalada.

Cómo pensar en módulos:
- Dominio: las reglas del negocio en limpio (no sabe de base de datos ni HTTP).
- Aplicación: orquesta casos de uso (coordina dominio y puertos).
- Infraestructura: detalles técnicos (bases de datos, seguridad, integraciones).
- API: lo que habla con el mundo exterior (HTTP/REST, DTOs, validación).
¿Qué pongo exactamente en cada carpeta?
- domain/model: clases que representan conceptos del negocio (Cliente, Cita).
- domain/valueobject: tipos con validaciones propias (Email, Cedula, Dinero).
- domain/repository: interfaces que dicen “qué” necesitamos de la BD (buscar cliente, guardar cita).
- application/usecase: clases que ejecutan un caso de uso completo (crear cliente, agendar cita).
- infrastructure/persistence/entity: entidades JPA (con anotaciones @Entity, @Table...).
- infrastructure/persistence/repository: interfaces Spring Data (extends JpaRepository...).
- infrastructure/persistence/adapter: puente entre repos del dominio e implementación JPA.
- api/dto: objetos para entrada/salida de la API; nunca expongas entidades JPA.
- api/controller: endpoints REST (GET/POST/PUT/DELETE) que llaman a los casos de uso.
- api/handler: manejo de errores y validaciones para respuestas limpias.
Buenas prácticas de estructura (aplican a casi cualquier proyecto Java/Spring):
  • Separar dominios en módulos o paquetes evita “mezcla” entre reglas de negocio y detalles técnicos.
  • Usar DTOs para la API: protege tu modelo interno y te permite evolucionarlo sin romper clientes.
  • Definir interfaces de repositorio en domain y sus implementaciones en infrastructure mantiene el dominio limpio.
  • Centralizar migraciones en infrastructure/resources/db/migration con Flyway/Liquibase.
  • Un GlobalExceptionHandler en la API asegura respuestas consistentes de error.
  • Mantener un README.md con cómo correr el proyecto y perfiles de Spring.
  • Usar .env.example para documentar variables de entorno sin exponer credenciales reales.

Cómo se conecta todo (se plantea un flujo típico y muy usado en proyectos profesionales)

  1. El Controller recibe una petición HTTP con un DTO.
  2. Valida el DTO y llama a un Use Case en application.
  3. El Use Case usa el Dominio (entidades/servicios) para aplicar reglas.
  4. Cuando necesita datos, llama a un Repositorio del Dominio (interface).
  5. Un Adapter en infrastructure implementa ese repositorio usando Spring Data JPA y mapea a entidades JPA.
  6. Se persiste en la BD, se regresa el resultado al Use Case, luego al Controller y se responde con un DTO.
Nota (palabras clave mencionadas en el flujo, que depronto no se comprendan a nivel general como ayuda o plus pensando en que todo sea comprensible tanto para ya profesionales como para novatos o estudiantes):
- DTO: “Data Transfer Object”. Objeto simple para enviar/recibir datos por la API. No contiene lógica, solo campos.
- Controller: clase que expone endpoints HTTP (REST). Recibe requests, valida y delega el trabajo.
- Use Case: caso de uso. Coordina pasos del negocio para cumplir una acción (crear cliente, agendar cita).
- Dominio: el corazón del negocio (entidades y reglas) sin depender de la base de datos ni de HTTP.
- Repositorio (del Dominio): interfaz que define qué operaciones de datos necesita el dominio (guardar, buscar), sin decir cómo se implementan.
- Adapter: “traductor” que implementa el repositorio del dominio usando una tecnología concreta (por ejemplo, JPA).
- JPA: “Java Persistence API”. Estándar para mapear objetos Java a tablas de base de datos y hacer CRUD sin escribir SQL puro.
- Spring Data JPA: librería de Spring que simplifica JPA (crea repositorios e implementaciones con muy poco código).
- Entidad JPA: clase anotada con @Entity que representa una tabla en la base de datos.
- BD: base de datos. Lugar donde se guardan los datos de forma persistente.
- API: interfaz para que otros sistemas o el frontend se comuniquen con tu aplicación vía HTTP (JSON, etc.).
- Validación: reglas para asegurar que los datos que entran tienen el formato y valores correctos antes de procesarlos.

Ejemplo mínimo de archivos clave

// Módulo: vete-domain // Paquete: com.vete.domain.repository package com.vete.domain.repository; import java.util.Optional; import com.vete.domain.model.Cliente; // Repositorio del Dominio: define QUÉ operaciones necesita el dominio. // No depende de JPA ni de Spring. Es una interfaz pura. public interface ClienteRepository { Optional findByCedula(String cedula); Cliente save(Cliente cliente); } // ------------------------------------------------------------- // Módulo: vete-infrastructure // Paquete: com.vete.infrastructure.persistence.repository package com.vete.infrastructure.persistence.repository; import java.util.Optional; import org.springframework.data.jpa.repository.JpaRepository; import com.vete.infrastructure.persistence.entity.ClienteEntity; // Repositorio JPA: implementado por Spring Data JPA. // Aquí ya hablamos en términos de entidades JPA (ClienteEntity). public interface ClienteJpaRepository extends JpaRepository { Optional findByCedula(String cedula); } // ------------------------------------------------------------- // Módulo: vete-infrastructure // Paquete: com.vete.infrastructure.persistence.adapter package com.vete.infrastructure.persistence.adapter; import java.util.Optional; import org.springframework.stereotype.Component; import lombok.RequiredArgsConstructor; import com.vete.domain.repository.ClienteRepository; // Puerto del dominio import com.vete.domain.model.Cliente; // Modelo del dominio import com.vete.infrastructure.persistence.repository.ClienteJpaRepository; // Repo JPA import com.vete.infrastructure.persistence.entity.ClienteEntity; // Entidad JPA import com.vete.infrastructure.mapper.ClienteEntityMapper; // Mapper (infra): Entity <-> Domain // Adapter: traduce entre el Dominio y JPA. // Implementa el puerto del dominio usando una tecnología concreta (Spring Data JPA). @Component @RequiredArgsConstructor public class ClienteRepositoryAdapter implements ClienteRepository { private final ClienteJpaRepository jpa; private final ClienteEntityMapper mapper; @Override public Optional findByCedula(String cedula) { // 1) Consultamos la BD con el repositorio JPA (retorna Entity) // 2) Mapeamos a modelo de Dominio antes de devolverlo al caso de uso return jpa.findByCedula(cedula).map(mapper::toDomain); } @Override public Cliente save(Cliente cliente) { // 1) Mapeamos del Dominio -> Entity JPA // 2) Guardamos con JPA // 3) Devolvemos el resultado mapeado a Dominio (por si cambia el ID u otros campos) ClienteEntity saved = jpa.save(mapper.toEntity(cliente)); return mapper.toDomain(saved); } }

Así el Dominio no depende de JPA ni de Spring; solo conoce interfaces. La Infraestructura se encarga de los detalles técnicos, mapeando entre modelo de dominio y entidades JPA. Este patrón mantiene el código limpio y fácil de probar.

Nota de ayuda: Si eres novato o estudiante algo inexperto : empieza copiando esta estructura tal cual. A medida que crezcas, ajustarás nombres y capas según tu proyecto. Lo importante es que cada cosa tenga su lugar y que no mezcles reglas de negocio con detalles técnicos.

9. Calidad, rendimiento y seguridad (planteamiento inicial de lo que mínimamente debemos cubrir)

Rendimiento

  • Listados grandes con paginación (para no traer miles de registros de una).
  • Crear índices en campos que se buscan mucho (cédula, fecha de cita).
  • Caché opcional para catálogos que casi no cambian.

Seguridad

  • Inicio de sesión con tokens (JWT) y roles: ADMIN, VET, AUX, CLIENTE.
    JWT: al iniciar sesión, el servidor entrega un “pase digital” firmado que el cliente envía en cada petición. El servidor verifica la firma para saber quién eres y qué puedes hacer sin guardar sesión en memoria.
  • Contraseñas guardadas con BCrypt (encriptadas, no en texto plano).
    BCrypt: algoritmo para “hashear” contraseñas. No guarda la contraseña real, guarda un hash irreversible con sal. Si roban la base, no pueden ver tus contraseñas.
  • Auditoría básica: quién creó/cambió y cuándo.
    Guardar campos como creadoPor, creadoEn, actualizadoPor, actualizadoEn. Útil para trazabilidad y seguridad.

Mantenimiento

  • Pruebas unitarias y de repositorios usando H2.
    H2: base de datos en memoria para pruebas rápidas. Permite validar consultas y repositorios sin depender de la BD real.
  • Nombres claros y consistentes en paquetes y clases.
    Facilita encontrar código y reduce errores. Usa convenciones estables: controller, service, repository, dto, etc.
  • ADRs guardadas en el repositorio (para recordar por qué decidimos algo).
    ADR: “Architecture Decision Record”. Un archivo corto donde documentas una decisión técnica (qué problema resolviste, opciones evaluadas y la razón de la elección).
Índice: una “guía rápida” en la BD que acelera búsquedas en columnas muy consultadas (por ejemplo, cédula, fecha). Sin índice, la BD revisa fila por fila.
JWT: “JSON Web Token”. Token firmado que el servidor emite tras el login y el cliente envía en cada request para autenticación/autorización.
BCrypt: método seguro para almacenar contraseñas mediante hash con sal y costo (difícil de revertir o forzar).
H2: base de datos en memoria, ligera y rápida, ideal para pruebas automatizadas.
ADR: registro breve de una decisión de arquitectura: contexto, decisión, alternativas y consecuencias.
Roles: etiquetas que definen permisos. Ejemplo: ADMIN (todo), VET (gestión clínica), AUX (apoyo), CLIENTE (acceso propio).
