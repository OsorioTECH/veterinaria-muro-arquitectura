Proyecto: Aplicación Veterinaria "Muro"

1. Justificación y Problema a Resolver

Actualmente, la "Veterinaria Muro" gestiona su información de forma manual, lo que ocasiona retrasos, pérdida de tiempo, inconsistencias en los datos y molestias a los clientes.

El objetivo principal es diseñar una aplicación que automatice y centralice la gestión de historias clínicas, citas y facturación, mejorando la calidad del servicio y posicionando a la veterinaria en un nivel competitivo.

2. Modelo de Desarrollo Propuesto

Metodología Ágil (Scrum)

  • Flexibilidad: Permite incorporar cambios de requisitos durante el desarrollo.
  • Entregas parciales: Cada Sprint produce una funcionalidad usable (ej: módulo de citas).
  • Colaboración: El cliente participa activamente con retroalimentación continua.
  • Reducción de riesgos: Problemas se detectan temprano en ciclos cortos.

Alcance

  • Incluye: Gestión de clientes, mascotas, citas, facturación, servicios, exámenes clínicos, historial médico e informes.
  • No incluye: Integraciones externas, aplicaciones móviles nativas ni telemedicina.

Restricciones

  • Uso de Java y frameworks compatibles
  • Infraestructura de bajo costo
  • Acceso vía web

Suposiciones

  • Conexión a Internet estable
  • Personal capacitado en informática básica
  • Clientes con acceso a dispositivos con navegador

7. Diseño Arquitectónico
7.1 Racional Arquitectónico

Estilo elegido: Arquitectura en Capas

Justificación: Separación modular facilita el mantenimiento y escalabilidad. Se contemplan capas de Presentación, Lógica de Negocio y Datos.

Decisiones Clave

  • Lenguaje: Java
  • Base de datos: MySQL/MariaDB
  • Framework: Spring Boot
  • Gestión de versiones: GitHub
7.2 Vistas Arquitectónicas
Vista Lógica (Componentes)

Componentes principales: Clientes, Mascotas, Citas, Servicios, Facturación, Exámenes, Informes, Administración.

Vista de Proceso

Ejemplo: Flujo de asignación de citas.

Vista de Despliegue

El sistema se despliega en un servidor con base de datos MySQL y acceso vía web desde PCs/tablets.

7.3 Decisiones Arquitectónicas (ADR)
ADR-001 – Seguridad de Datos

Contexto: La aplicación maneja información sensible de clientes y mascotas (datos personales e historial clínico). Es necesario garantizar confidencialidad e integridad.

Decisión: Implementar encriptación de contraseñas con bcrypt y comunicación segura mediante HTTPS/TLS.

Consecuencias:

  • Positivo: Mayor protección frente a ataques de terceros.
  • Negativo: Sobrecarga mínima en rendimiento por encriptación y certificados.
ADR-002 – Rendimiento y Respuesta Rápida

Contexto: El sistema debe soportar múltiples usuarios consultando y registrando información en tiempo real sin retrasos.

Decisión: Uso de caché en consultas frecuentes (ej. historial de mascotas) y optimización de consultas SQL con índices.

Consecuencias:

  • Positivo: Reducción significativa de tiempos de respuesta.
  • Negativo: Riesgo de desactualización si el caché no se invalida correctamente.
ADR-003 – Escalabilidad

Contexto: Se proyecta un crecimiento en la cantidad de clientes y consultas conforme la veterinaria expanda sus servicios.

Decisión: Adoptar arquitectura en capas con separación clara de responsabilidades y posibilidad futura de migrar a microservicios.

Consecuencias:

  • Positivo: Facilita la incorporación de nuevos módulos (ej. telemedicina).
  • Negativo: Requiere mayor esfuerzo inicial en diseño para modularidad.
ADR-004 – Mantenibilidad

Contexto: El sistema será utilizado a largo plazo, con probables cambios en requisitos funcionales.

Decisión: Uso de Spring Boot con patrones de diseño (DAO, MVC) y documentación de código.

Consecuencias:

  • Positivo: Facilidad de adaptación a cambios, incorporación de nuevos desarrolladores.
  • Negativo: Aumento inicial en la curva de aprendizaje para el equipo.
